# 프렙 카페 기술 요구사항 문서(TRD)

작성일: 2026-10-12  
대상: PRD·FRD에서 확정한 1차 제품  
상태: 구현 기준 문서. 코드 작성·GitHub 업로드·Vercel 배포는 아직 수행하지 않음.

TRD는 프로그램을 어떤 기술과 구조로 만들고, 데이터를 어떻게 보관하며, 정확성과 장애를 어떻게 검사할지 정리한 문서다.

## 1. 근거와 설계 원칙

근거는 `docs/01_PRD.md`, `docs/02_FRD.md`, `design/artisan_ops/DESIGN.md`, `design/_1`~`_4`의 HTML·화면 이미지다. PRD의 기능 범위와 FRD의 입력·처리 순서·계산 C01~C09를 그대로 구현한다. PRD에 미정으로 남아 있으나 FRD에서 구체화한 상세 기준은 FRD를 적용한다. 새로 드러난 문서 충돌은 기술 편의로 계산을 바꾸지 않고 해당 부분을 확인 대상으로 보고한다.

사용자는 한 매장·한 운영자이며 FRD에서 로그인·다른 기기 자동 공유·클라우드 동기화를 제외했다. 따라서 1차는 **브라우저에서 계산·저장하는 웹 프로그램**으로 만든다. 서버 데이터베이스와 운영자료를 받는 서버 API는 두지 않는다. API는 프로그램끼리 자료를 주고받는 통로를 뜻한다.

GitHub는 코드·문서·검사 자료를 보관하고 Vercel은 웹 프로그램 파일을 제공한다. 운영자가 입력한 기록은 해당 기기의 브라우저에 보관하고 전체 JSON 파일로 백업한다. GitHub나 Vercel에 배포했다고 운영 기록이 자동 백업되는 것은 아니다.

여러 브라우저·기기에서 같은 자료를 자동 조회하는 제품은 아니다. 한 운영자가 기기를 바꾸려면 기존 기기에서 백업하고 새 기기에서 복원해야 한다. 로그인이나 서버 동기화가 필요해지는 경우 별도 기능 승인과 재설계가 필요하다.

## 2. 채택 기술

| 영역 | 기술 | 쉬운 설명과 선택 이유 |
| --- | --- | --- |
| 화면 | React + TypeScript | 화면을 재사용 가능한 부분으로 나누고, 자료 항목을 잘못 연결하는 실수를 개발 중 발견 |
| 개발·빌드 | Vite + npm | 개발 화면을 빠르게 실행하고 Vercel에 올릴 HTML·CSS·JS 파일 생성 |
| 스타일 | CSS Modules + CSS 변수 | 시안의 색·간격·글꼴 규칙을 공통 적용. 시안의 외부 CDN·인라인 스크립트 의존 제거 |
| 화면 이동 | URL 해시 기반 경로 | `/#/sales`처럼 주소 뒤에서 화면을 구분. 새로고침 시 서버 경로 설정 문제를 줄임 |
| 브라우저 저장 | IndexedDB + Dexie | 브라우저 안의 구조화된 저장소. 여러 변경을 전부 성공 또는 전부 취소하도록 묶기 쉬움 |
| 숫자 계산 | decimal.js | 원가·평균 단가 같은 소수 계산의 오차를 관리하고 지정 위치에서 반올림 |
| 입력·파일 검사 | Zod + 별도 업무 규칙 검사 | 필수 항목·형식과 메뉴 참조·중복·날짜 등 업무 조건을 함께 확인 |
| JSON 수치 보존 | lossless-json | 숫자를 읽고 쓸 때 원래 소수 자릿수가 일반 숫자 변환에서 사라지는 문제 방지 |
| 계산 검사 | Vitest | FRD 계산과 재고·비용 규칙을 자동 검사 |
| 브라우저 검사 | Playwright | 실제 화면의 입력·저장·재실행·파일 다운로드·복원 검사 |
| 코드 보관·배포 | GitHub 비공개 저장소 + Vercel 정적 배포 | 코드와 실행 파일을 관리하며 운영자료를 서버에 보내지 않는 구조 |

Node.js는 개발·빌드용으로 22.x의 22.12 이상을 기준으로 한다. 설치 시 Vite·Vitest·Vercel 빌드 환경에서 함께 지원되는 안정 버전을 확인하고, 실제 선택 버전은 `package.json`, `package-lock.json`, Node 버전 설정에 고정한다. 배포할 때마다 자동으로 최신판을 설치하지 않고 `npm ci`로 같은 버전을 설치한다. Vite와 Vitest의 요구 환경은 [Vite 안내](https://vite.dev/guide/)·[Vitest 안내](https://vitest.dev/guide/)를 기준으로 확인한다.

Next.js 서버 기능, 외부 DB, 계정 서비스, 결제 연동, PWA 설치·완전 오프라인 실행은 1차에 도입하지 않는다. 새 기능이 필요해서가 아니라 현재 FRD의 브라우저 처리에 필요한 최소 기술을 선택한 것이다. Vercel의 Vite 배포 지원은 [공식 배포 문서](https://vercel.com/docs/frameworks/frontend/vite)를 근거로 한다.

## 3. 전체 구조와 코드 책임

```text
GitHub 코드 → Vercel 빌드 → 프로그램 파일을 브라우저에 제공
                                  ↓
화면 입력 → 입력·업무 검사 → 공통 계산 → 저장 서비스 → IndexedDB
                              ↑                       ↓
                     화면별 조회·집계 ← 저장 성공한 동일 기록

IndexedDB의 전체 기록 → JSON 백업 파일
사용자 JSON 파일 → 검사·내용 확인 → 전체 복원 → IndexedDB
```

계산과 저장을 화면 코드에서 직접 수행하지 않는다. 화면은 사용자 입력·확인·결과 표시를 맡고, 계산 모듈은 FRD 규칙을 맡으며, 저장 서비스만 보관 자료를 변경한다. 여러 화면이 같은 계산 함수를 사용해 판매표·메뉴표·손익표의 금액이 달라지지 않게 한다.

| 파일·폴더 계획 | 책임 |
| --- | --- |
| `src/app/` | 공통 화면 틀, 해시 경로, 프로그램 시작·오류 경계 |
| `src/features/sales/` | F02~F04 판매 입력·미리보기·목록·수정·삭제 |
| `src/features/profitability/` | F05 메뉴별 수익성과 근거 조회 |
| `src/features/dashboard/` | F01·F06 기간 조회·실적·손익 |
| `src/features/inventory/` | F07 입고·폐기·실사·잔량 |
| `src/features/expenses/` | F08 비용 관리 |
| `src/features/data/` | F09~F10 저장 상태·백업·복원 |
| `src/domain/` | 자료 형식, C01~C09, 날짜·마감·재고 규칙, 검증 |
| `src/storage/` | IndexedDB, 저장 버전·트랜잭션·중복 요청 처리 |
| `src/io/` | 샘플 변환, 정밀 JSON 읽기·쓰기, 백업 검사 |
| `src/styles/` | 디자인 변수와 공통 테이블·입력·버튼 스타일 |
| `src/fixtures/` | 가상 샘플만 포함한 초기 자료 |
| `tests/` | 계산·저장·복원 검사와 브라우저 시나리오 |
| `docs/`, `design/` | 요구사항·시안. 원본 참고용이며 정적 공개 폴더로 복사하지 않음 |

경로 이름은 구현 기준이며 이 문서 작성으로 실제 코드를 생성한 것은 아니다.

## 4. 시안을 화면으로 옮기는 방법

5개 이동 메뉴는 대시보드, 판매, 메뉴 수익성, 재고, 비용·데이터로 연결한다. 해시 경로는 각각 `/#/dashboard`, `/#/sales`, `/#/profitability`, `/#/inventory`, `/#/expenses`로 통일한다. 비용·데이터 안에서 비용 관리와 백업·복원에 접근한다. 경로 이동 시 FRD에 따른 기간을 전달하고 재고 기준일은 별도로 표시한다.

시안 `_1`의 판매 입력을 공통 등록·수정 창으로 구현하고 실제 결제수수료 칸을 보완한다. `_2`의 조회·필터·페이지·행별 수정/삭제, `_3`의 일·월 손익, `_4`의 메뉴 수익성 표를 FRD 범위로 구현한다. 시안에 없는 비용·재고·보관 화면은 같은 입력·표·확인 창 구성요소로 만든다.

시안 HTML을 그대로 실행 파일로 쓰지 않는다. 고정 예시 데이터·원가율 25%·수수료 2.5%·고정 판매일·가짜 동기화 완료 문구를 제거하고 저장된 자료·공통 계산 결과로 연결한다. 추세 표시가 필요한 경우 공통 집계값을 이용한 간단한 SVG로 구성하며 별도 분석 기능을 추가하지 않는다.

`DESIGN.md`의 색·간격·숫자 정렬을 CSS 변수로 옮기고 실제 시안의 화면 구성을 우선한다. 한글 글꼴은 운영체제 기본 한글 글꼴로 대체하고 외부 Google Fonts 요청은 사용하지 않는다. 아이콘은 필요한 것만 로컬 SVG로 제공한다. 시안의 모든 버튼을 실행 가능하게 만드는 것이 아니라 FRD 대응표에 따라 1차·2차·미승인을 구분한다.

실행 대상인 1차 조작은 모두 키보드로 사용할 수 있어야 한다. 입력 이름·단위·오류를 연결하고 창을 닫으면 원래 버튼으로 초점을 돌린다. 좁은 화면에서는 표에 가로 스크롤을 제공해 금액·관리 버튼을 잘라 숨기지 않는다. 색만으로 확정/미확정·오류를 구분하지 않는다.

## 5. 저장할 자료의 형식

### 5.1 운영 자료 묶음

1차는 약 1만 건의 자료를 하나의 일관된 자료 묶음으로 보관한다. 서버 테이블을 흉내 내 여러 곳에 같은 합계·재고를 중복 저장하지 않는다.

| 자료 | 저장할 내용·식별 기준 |
| --- | --- |
| 출처·설정 | 원본 meta, 매장·통화·시작일, 자료 형식 버전, 계산 기준 버전, 시간대 `Asia/Seoul` |
| 기초 정보 | 공급사, 재료·기준단위·구매용량, 메뉴, 레시피 버전·채널 조건, 적용일 가격이력 |
| 영업달력 | 날짜별 영업 여부·마감 여부·메모. 없는 날짜를 자동 마감 완료로 만들지 않음 |
| 판매 | 판매번호, 날짜·메뉴·채널, 수량·단가·총 할인·순매출·수수료, 당시 원가·레시피 버전 |
| 초기재고 | 재료번호·기준일·수량·단위 |
| 재고 기록 | 기록번호·날짜·재료·유형·증감량·실측량·사유·공급사·입고 단위원가 |
| 비용 | 비용번호·귀속일·기존 8개 항목·금액·기록 출처·배분기준 |
| 월비용계획 | 월·항목·금액. 실제 비용 집계와 분리 |
| 보존 근거 | 원본 기록값, 수정 후 적용 원가·레시피·가격 근거. 화면에 새 감사 기능은 추가하지 않음 |

수입 자료와 새 입력을 구분하는 `origin` 값과 변경 확인용 `recordVersion`을 둔다. 원본 판매의 금액과 개당 소수 원가는 보존한다. 원가 근거 조회와 수정 정책을 위해 원본 값과 현재 유효 값을 구분하며 과거 편집 이력 화면은 만들지 않는다.

판매는 `[날짜, 메뉴번호, 채널]`, 실측 입력은 `[날짜, 재료번호]`가 중복되면 안 된다. 비용은 같은 날짜·항목이라도 여러 건 허용하고 FRD의 완전 동일 재입력 확인을 적용한다. 신규 번호는 UUID로 생성해 원본의 판매·비용번호와 충돌하지 않게 한다.

### 5.2 숫자·날짜 표현

업무 날짜는 `YYYY-MM-DD`, 귀속월은 `YYYY-MM`로 저장한다. UTC 시각으로 변환했다가 날짜가 전날로 바뀌는 처리를 하지 않는다. 오늘 판정과 백업 파일명 표시는 `Asia/Seoul`을 사용하며 기기 시계 오차 가능성을 안내할 수 있다.

금액·단가·수량은 IndexedDB 안에서는 정규화한 십진수 문자열로 보관하고 계산 시 Decimal로 변환한다. 이는 `₩1,000` 같은 표시 문자열이 아니라 정밀한 수치 보관 형식이다. 백업 JSON에는 lossless-json으로 실제 숫자 토큰으로 써서 FRD의 수치 보존 요구를 지킨다. 일반 `Number`로 먼저 변환하지 않는다. 빈칸은 `null` 또는 원본의 해당 없음 상태로 구분하고 0으로 치환하지 않는다. 소수 처리 근거는 [decimal.js](https://mikemcl.github.io/decimal.js/)와 [lossless-json](https://github.com/josdejong/lossless-json)을 따른다.

신규 입력은 FRD의 정수 원·양의 정수 판매수량·g/ml 소수 3자리·개 정수 규칙을 검사한다. 원본의 기존 값은 해당 원본 규칙으로 검사하여 신규 입력 정밀도 제한 때문에 원본 소수를 잘라 버리지 않는다. 처리할 수 없는 숫자는 오류로 거부하며 999 같은 업무 상한을 새로 두지 않는다.

## 6. 브라우저 저장과 변경의 일관성

### 6.1 IndexedDB 구성

Dexie DB 이름은 `prep-cafe-ops`, 초기 스키마는 1로 한다. 앱 배포 번호가 바뀌어도 DB 이름을 바꾸지 않는다.

| 저장 영역 | 용도 |
| --- | --- |
| `datasets` | 고정 키 `active`의 현재 전체 자료 묶음, `revision`, 초기화 완료 상태, 최근 성공 저장 시각, 자료 형식 버전 |
| `operations` | 요청번호·결과·반영 revision. 재클릭·재시도를 한 번만 적용하기 위한 내부 기록 |

이 구조는 현재 약 3.46MB 원본 JSON 규모에서 저장·전체 복원을 단순하게 만들기 위한 선택이다. 조회용 날짜·메뉴·재료 색인은 메모리에서 만들고, 더 큰 운영 규모에서 별도 테이블 색인이 필요하면 성능 측정 후 저장 계층만 개선한다. FRD의 기능·계산은 바꾸지 않는다.

### 6.2 기록 변경 순서

1. 현재 자료와 `revision`을 읽고 사용자 입력·필수 확인을 완료한다.
2. 메모리에서 변경 후보를 만들고 업무 검증·공통 계산·음수 잔량 확인을 한다. 사용자 확인 창은 DB 저장을 시작하기 전에 완료한다.
3. Dexie 읽기/쓰기 트랜잭션으로 `datasets`와 `operations`를 함께 연다. 트랜잭션은 변경을 전부 성공하거나 전부 취소하는 묶음이다.
4. 같은 요청번호가 이미 반영됐으면 중복 실행하지 않고 기존 결과를 돌려준다. 그렇지 않으면 현재 revision이 1단계와 같은지 확인한다.
5. 같으면 새 자료·증가한 revision·최근 저장 시각·요청 처리 결과를 함께 저장한다. 다르면 오래된 수정으로 덮어쓰지 않고 재조회 안내한다.
6. 트랜잭션 완료 후에만 성공 안내와 화면 자료 교체를 한다. 그전에는 기존 확정 화면·초안을 유지한다.

같은 저장 시도의 요청번호는 재시도에도 유지한다. 새 편집은 새 요청번호를 쓴다. 다른 탭의 변경은 Dexie 변경 구독으로 감지하며 입력 중 초안을 자동 덮어쓰지 않는다. 한 운영자가 여러 탭을 열어도 오래된 창이 최신 자료를 지우지 않게 한다. 비동기 조회 결과에는 revision과 조회 조건 식별값을 붙여 늦게 도착한 이전 조회가 최신 화면을 덮지 않게 한다.

트랜잭션 중 파일 읽기·네트워크 요청·사용자 확인·타이머를 기다리지 않는다. 필요한 비동기 처리는 바깥에서 끝낸다. 예외를 내부에서 삼켜 성공으로 바꾸지 않는다. 이 제한은 [Dexie 트랜잭션 안내](https://dexie.org/docs/Dexie/Dexie.transaction())를 따른다.

### 6.3 보관 한계

IndexedDB는 사이트 주소와 브라우저 프로필별로 분리된다. 같은 기기의 Chrome과 Edge, Vercel 미리보기 주소와 운영 주소는 별도 자료다. 배포 주소가 달라지면 이전 자료가 자동 이동하지 않는다. 브라우저 저장 특성과 한계는 [MDN 저장 안내](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)를 근거로 한다.

첫 저장 후 `navigator.storage.persist()`로 지속 저장을 요청하고 `estimate()`로 예상 용량을 확인한다. 지속 저장이 거부되어도 사용은 가능하지만 상태를 안내하며 이를 파일 백업으로 오해시키지 않는다. 지속 저장도 사용자의 사이트 데이터 삭제나 기기 고장을 막지 못한다. 비공개 창·임시 프로필은 장기 운영에 사용하지 않도록 보관 안내에 명시한다. 지속 저장의 반환값은 [StorageManager.persist 안내](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)를 따른다.

DB 읽기에 실패했을 때 메모리 저장으로 몰래 전환해 저장 성공을 표시하지 않는다. 오류로 중단하고 원본·초안을 보존한다. 모든 사이트 자료가 삭제된 경우 최초 사용과 구분할 확실한 흔적도 함께 사라질 수 있으므로 자동 감지·복구를 보장하지 않는다. 이 한계 때문에 별도 JSON 백업이 필요하다.

## 7. 계산 모듈 구현

`src/domain/`에 입력이 같으면 결과가 같은 순수 함수를 둔다. 함수가 화면·DB를 직접 바꾸지 않게 해 미리보기와 실제 저장에 같은 계산을 사용한다.

| FRD | 구현 책임 |
| --- | --- |
| C01 | 정상 판매액의 기록 단위 원 반올림 후 총 할인 차감 |
| C02 | 재료·날짜별 가격 목록에서 판매일 이하 최신 가격 선택, 구매용량 환산, 레시피·채널 조건 적용 |
| C03 | 당시 또는 신규 개당 원가×수량. 식재료·포장 합계를 각각 기록 단위 반올림 |
| C04 | 순매출−식재료−포장−실제 수수료. 자동 수수료율 적용 없음 |
| C05 | 동일 기간·마감·필터별 금액 합산. 수익률은 합계 금액으로 계산 |
| C06 | 전체 메뉴 수익−귀속 운영비−명시적 폐기 손실. 월계획·입고대금 중복 제외 |
| C07 | 재료별 일자 순 증감과 마감 실측 기준 재설정. 미확정 판매도 실제 사용량에 반영 |
| C08 | 수량 기준 채널 비중, 페이지당 8건의 페이지 수 |
| C09 | 정상 판매액 합÷판매수량 합으로 평균 단가 표시 |

Decimal은 충분한 중간 정밀도(초기 40 유효숫자)와 `ROUND_HALF_UP`을 명시한다. 정밀도 한계를 넘어 결과를 신뢰할 수 없으면 범위 오류로 중단한다. 신규 기록의 C01/C03/C06에서만 원 단위 반올림하며 화면 합계는 해당 기록 금액의 합을 사용한다. 비율은 소수 1자리, g/ml 잔량은 소수 3자리로 표시한다. 표시 반올림을 다시 원장에 저장하지 않는다.

재료 구분은 제공 자료의 포장 전용 레시피·재료번호 대응을 명시적으로 고정해 적용한다. 이름에 '컵'이 있는지 같은 추측으로 분류하지 않는다. 현재 자료의 포장컵세트 I10·디저트포장세트 I11을 확인된 포장 재료로 연결한다. 해당 대응 정보도 백업에 포함한다.

판매의 수량·단가·할인 수정은 당시 원가·레시피 유지, 날짜·메뉴·채널 변경은 FRD F04 기준 재산정한다. 재료가격이 바뀌었다는 이유만으로 과거 전체를 재평가하지 않는다. 신규 폐기는 폐기일 적용가격과 산정 근거를 기록하고 손익에서 한 번만 차감한다. 실사 차이로 자동 폐기 비용을 만들지 않는다.

재고는 초기재고 → 해당일 입고 → 판매 사용량·폐기 → 당일 마감 실사 순서다. 실측값이 있으면 그 값으로 잔량을 교체하고 함께 있는 조정량을 다시 더하지 않는다. 실측 없는 조정량만 증감한다. 실사 전 판매 수정은 실사 차이를 바꾸지만 뒤의 실측 기준을 넘어 현재 잔량을 바꾸지 않는다. 실사 이후 변경은 이후 잔량에 반영한다.

마감 집계는 달력 상태를 참조한다. 확정 실적과 미확정 입력 실적을 다른 결과 묶음으로 반환하고, 재고는 둘 다 실제 저장 판매로 사용한다. 누락·자료 없음·0·음수·계산 불가를 결과 상태로 구분해 반환한다. 모든 화면이 이 상태를 동일하게 표시한다.

## 8. 초기 자료 가져오기와 2차 엑셀 확장

### 8.1 1차 초기 자료

현재 원본 JSON 크기는 3,455,500바이트, 엑셀은 490,677바이트다. 1차는 JSON 하나를 초기 가상 자료로 사용하고 엑셀을 실행 중 다시 읽지 않는다. JSON을 정밀하게 읽고 원본 스키마·참조·중복·단위·필수 항목을 검사한 뒤 내부 자료 묶음으로 변환한다.

초기자료에는 출처번호 `dataset_id`·원본 version·시작일·마감일을 보존한다. 레시피의 빈 채널은 모든 채널 적용으로, 마감 여부의 불리언은 원본 의미대로 변환한다. 원본 빈칸을 0으로 바꾸지 않는다.

DB에서 초기화 완료 표시와 active 자료가 모두 없고 정상적으로 읽힌 최초 사용에만 초기 자료를 한 번 저장한다. 기존 active 자료가 유효하지만 판매가 0건인 경우, 복원한 0건 자료인 경우에는 샘플을 재삽입하지 않는다. 표시와 자료 상태가 서로 맞지 않거나 읽기에 실패하면 샘플로 덮지 않고 오류 안내한다. 최초 저장도 전부 성공/취소 트랜잭션으로 처리한다.

샘플 파일은 브라우저가 내려받으므로 배포에 포함하면 공개된다. 현재 제공 자료의 가상 샘플만 포함하며 실제 매장 기록을 초기 배포 파일로 바꿔 넣지 않는다. 원본을 운영 데이터로 반복 수입하는 메뉴를 새로 추가하지 않는다.

### 8.2 2차 엑셀 가져오기

2차에 승인된 입력 양식·가져오기를 구현할 때 `src/io/`에 별도 XLSX 어댑터를 연결한다. 브라우저에서 파일을 읽고 검증한 뒤 동일한 저장 서비스를 호출한다. 수식·매크로를 실행하지 않으며 허용한 열·날짜·메뉴·단위만 읽는다. 파일 처리 라이브러리는 2차 착수 시 유지보수·취약점·라이선스를 확인해 선정하고 그때만 설치한다.

전부 중단/정상 행만 반영, 중복 처리, 수식 셀 허용 등은 FRD의 2차 미정 정책이다. TRD에서 임의 결정하거나 1차 버튼을 활성화하지 않는다. 원본 JSON 가져오기·백업 복원·엑셀 행 수입을 서로 다른 파일 규약으로 구분한다.

## 9. 전체 백업·복원 구현

### 9.1 백업 파일

제품 전용 식별자 `prep-cafe-ops-backup`과 `backupFormatVersion: 1`, 자료 스키마·계산 버전, 생성시각, 원본 meta, 전체 운영 자료·기초 정보·영업달력·제품 설정을 포함한다. `data` 안에는 원본 출처와 현재 유효 기록을 복원할 수 있는 자료를 담는다. 표시용 합계·임시 미리보기·미저장 초안·다른 탭의 임시 상태는 포함하지 않는다.

백업 버튼을 누른 시점의 저장된 active 자료를 한 번 읽어 일관된 스냅샷(그 시점의 전체 사본)을 만든다. JSON 숫자를 lossless-json으로 직렬화하고 `Blob`·임시 다운로드 링크로 내려받는다. 파일명은 FRD의 한국 시간 규칙을 따른다. 내려받기 후 임시 객체 URL을 해제한다. 파일 생성 실패와 다운로드 시작을 구분하며 기기의 파일 저장 완료를 확인했다고 표시하지 않는다.

파일은 평문 JSON이다. 암호화·비밀번호 기능을 새로 넣지 않으며 내려받은 파일을 USB·보호된 폴더 등 운영자가 관리하는 위치에 보관하도록 안내한다. GitHub에 백업을 올리지 않는다.

### 9.2 복원

파일 선택 → 용량·UTF-8 JSON 구문 검사 → 제품 식별자·버전 검사 → 자료 구조·참조·중복·단위·수치 검사 → 메모리에서 계산 가능성 점검 → 현재/복원 기록 수·기간과 전체 대체 안내 → 사용자 확인 → active 전체 대체 트랜잭션 → 재집계 순서를 따른다.

중복 JSON 속성명이나 허용하지 않은 구조를 거부하고, 읽어들인 객체를 실행하거나 기존 설정 객체에 무제한 합치지 않는다. 0바이트·손상·일반 원본 운영 JSON을 제품 백업으로 자동 처리하지 않는다. 정상 구조와 필수 기초 정보를 갖춘 활동 기록 0건 백업은 FRD의 명시적 확인 후 허용한다.

사용자가 확인하는 사이 다른 탭에서 기록이 바뀌면 revision 불일치로 중단하고 현재 내용을 다시 확인시킨다. 성공 시 전체 대체와 로컬 revision 증가, 초기화 완료 표시, 이전 요청 영수증 초기화를 같은 트랜잭션에 넣고 해당 복원 요청의 완료 영수증을 남긴다. 백업 안의 revision으로 로컬 revision을 되돌리지 않는다. 이전 창의 저장 요청은 구 revision이어서 거부되고 같은 복원 요청의 재시도는 이미 처리된 결과를 반환한다. 새 입력 요청은 새 요청번호를 사용한다.

검사·확인 전에 현재 자료를 지우지 않는다. 실패·취소는 이전 active 그대로 유지한다. 복원 전 현재 자료의 JSON 백업을 권유하되 자동 파일 생성이나 자동 병합을 추가하지 않는다. 파일 크기를 먼저 확인해 큰 파일은 시간이 걸릴 수 있음을 안내한다. 크기만으로 정상 백업을 다른 형식이라고 거부하거나 일부만 반영하지 않는다. 실제 메모리·저장 용량 부족이 발생하면 기존 자료를 유지하고 오류를 안내한다. 처리 속도 보장 범위는 11절의 제공 자료 규모이며, 범위 확대는 저장·검사 구현을 개선해 대응한다.

| GitHub | 비공개 저장소를 기본으로 하고 실제 기록·백업·토큰·비밀번호는 커밋하지 않음 |
| 백업 파일 | 평문으로 내려받으므로 파일 접근 권한과 별도 보관이 필요. 브라우저 저장 삭제와 별개로 관리 |
| 접속 정보 | 앱이 업무 자료를 전송하지 않아도 Vercel 접속 과정의 IP·브라우저 등 기술 로그가 남을 수 있음. '어떤 정보도 전송하지 않음'이라고 안내하지 않음 |

GitHub 공개/비공개 저장소의 접근 차이는 [GitHub 공식 안내](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories)를 따른다. 비공개 저장소여도 정적 배포 파일 자체가 비공개가 되는 것은 아니다.

시안의 외부 폰트·아이콘·Tailwind CDN 스크립트를 빌드 산출물로 대체한다. React의 기본 텍스트 렌더링을 사용하고 메모·사유·파일 내용을 HTML로 삽입하지 않는다. 백업에서 `__proto__` 등 예상 밖 필드는 허용 목록 기반 검증으로 제외 또는 거부한다.

Vercel 응답 헤더에 CSP(허용한 파일만 실행하는 정책), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `frame-ancestors 'none'`을 적용한다. CSP의 기본·스크립트·스타일·폰트·연결은 동일 출처만 허용하고, 불필요한 외부 연결·객체 실행을 막는다. `Permissions-Policy`로 사용하지 않는 카메라·마이크·위치 권한을 차단한다. CSP는 Vite 개발 서버와 운영 빌드를 구분해 실제 배포에서 입력·파일 다운로드가 동작하는지 검사한다.

오류 콘솔·테스트 보고서에는 원장 전체·백업 전문·메모·실제 이름을 출력하지 않는다. 운영용 원격 오류 수집·분석 SDK는 도입하지 않는다. `VITE_`로 시작하는 빌드 변수는 사용자에게 전달될 수 있으므로 비밀을 넣지 않는다. 이 구조는 런타임 비밀키를 요구하지 않는다.

## 11. 처리 속도·용량 기준

아래는 현재 제공 자료 약 1만 건·원본 JSON 3.46MB를 기준으로 한 **목표이며 측정 결과가 아니다**. Windows 일반 PC, 최신 안정 Chrome·Edge, 배포 파일이 정상 전달되는 환경에서 측정한다.

| 작업 | 목표 |
| --- | --- |
| 첫 시작·초기 자료 검사·DB 저장·표시 | 자료 다운로드 후 5초 이내 |
| 조회 기간·메뉴·채널 변경 | 로딩 완료 후 500ms 이내 |
| 입력 미리보기 | 150ms 이내 |
| 기록 저장·관련 화면 반영 | 1초 이내 |
| 전체 백업 파일 준비 | 3초 이내 |
| 제공 자료 규모 복원 검사·대체 | 사용자 확인 대기 제외 5초 이내 |

각 작업은 최소 20회 측정해 p95(20번 중 느린 쪽에 가까운 값)를 확인한다. 기기·브라우저·파일크기·네트워크 조건을 보고서에 남긴다. 10배 자료에서도 숫자·저장 정확성·오류 처리는 검사하되 같은 속도를 보장한다고 주장하지 않는다.

한 번 읽은 자료의 메뉴·재료·가격이력은 Map으로 연결하고 기간·레시피 사용량을 revision별로 재사용한다. 화면 표는 현재 8행만 렌더링한다. 매 키 입력마다 전체 6,112건의 원가를 재산정하지 않고 해당 입력의 변동과 영향 재료만 미리 계산한다. 저장 후에는 해당 revision의 결과로 갱신한다.

성능이 기준에 못 미치면 먼저 반복 계산·불필요한 전체 직렬화·재렌더링을 줄인다. 대용량에서 필요할 때 계산을 Web Worker(화면과 별도로 계산하는 작업 공간)로 옮길 수 있으나 1차 기본 의존으로 추가하지 않는다. 최적화 때문에 반올림·실사·미확정 포함 규칙을 바꾸지 않는다.

초기 샘플은 최초 사용 시에만 다운로드·변환하고 저장 자료가 있으면 다시 덮지 않는다. 지속 저장·실제 남은 용량은 브라우저마다 다르므로 용량 추정값을 절대 보장으로 사용하지 않는다. 실패 시 기존 자료를 삭제해 공간을 자동 확보하지 않는다.

## 13. GitHub 보관과 Vercel 배포

### 13.1 저장소와 검사

GitHub에는 소스·문서·시안 참고·가상 샘플·검사 코드·버전 고정 파일·배포 설정을 보관한다. `.gitignore`에는 `node_modules/`, `dist/`, `.vercel/`, `.env*`(비밀 없는 예시 파일 제외), 실제 운영자료 보관 폴더·백업·실제 자료가 들어갈 수 있는 검사 결과물을 제외한다. 가상 샘플만 별도 명시 경로로 관리해 모든 JSON을 일괄 제외하지 않는다.

현재 폴더 전체를 점검 없이 GitHub에 올리지 않는다. 최초 커밋 전 실제 자료·인증정보·다운로드 백업이 포함되지 않았는지 확인한다. 저장소 이름·소유 계정은 구현 시 실제 사용자가 사용할 대상으로 정한다. 1차 기준은 비공개 저장소다.

`main`은 운영 배포 기준으로 하고 작업 브랜치에서 변경·검사 후 반영한다. `npm run typecheck`, `npm run test -- --run`, `npm run build`가 통과해야 한다. 브라우저 핵심 시나리오도 배포 후보에서 검사한다. GitHub Actions를 사용할 경우 이 검사만 구성하고 실제 영업 자료를 테스트 입력으로 올리지 않는다.

### 13.2 Vercel 설정

GitHub 저장소를 Vercel 프로젝트에 연결한다. 프레임워크는 Vite, 설치는 `npm ci`, 빌드는 `npm run build`, 출력은 `dist`다. Node 버전은 로컬·검사·Vercel에서 일치시킨다. Vite 지원과 Git 기반 미리보기 배포는 [Vercel 공식 안내](https://vercel.com/docs/frameworks/frontend/vite)를 따른다.

해시 경로를 사용해 서버에 `/sales` 경로를 직접 요청하지 않는다. `vercel.json`에는 운영 보안 헤더와 캐시 정책을 명시한다. 해시가 붙은 자원은 장기 캐시, 시작 HTML은 재검증하도록 해 오래된 HTML이 없는 새 JS 파일을 가리키는 문제를 줄인다. 서비스 워커는 두지 않는다. 초기 인터넷 접속·파일 로딩이 필요하며 이후 네트워크가 끊긴 상태의 새 실행을 보장하지 않는다.

빌드에서 `dist`에 포함된 파일을 점검한다. `design/`, 문서, 원본 엑셀, 실제 JSON·백업, 테스트 보고서·비밀 설정을 공개 정적 파일로 복사하지 않는다. 가상 샘플 파일은 공개 가능성이 있는 자료로 취급한다. 운영 소스맵은 공개 배포하지 않는다.

### 13.3 운영 주소·미리보기·되돌리기

운영자는 고정된 Vercel 운영 별칭 주소를 사용한다. 배포별 임시 주소·Preview에서 입력한 자료는 운영 주소로 자동 이동하지 않는다. 기존 운영 주소에 새 코드를 배포하면 같은 브라우저 저장소를 이어 쓰되 코드는 데이터 스키마 호환 여부를 확인해야 한다.

주소·도메인 변경 전에는 기존 주소에서 전체 백업을 내려받고 새 주소에서 복원한다. 이전 사이트가 사라진 뒤 자료를 옮길 수 있다고 가정하지 않는다. 앱을 같은 출처의 다른 무관한 서비스와 섞어 호스팅하지 않는다.

장애 시 이전 검증된 Vercel 배포로 코드를 되돌릴 수 있지만 브라우저 자료도 자동으로 과거로 돌아가지는 않는다. 데이터 형식 변경이 있다면 이전 코드가 해당 형식을 읽을 수 있는지 먼저 확인한다. 코드 롤백으로 DB를 삭제하거나 샘플을 덮어쓰지 않는다.

## 14. 오류·버전 변경 대응

| 상황 | 기술 대응·화면 안내 |
| --- | --- |
| 필수값·날짜·수치·중복 오류 | 필드 오류와 원인 표시. DB 변경 전 중단, 초안 유지 |
| 레시피·가격 누락 | 해당 메뉴·재료·일자 표시, 신규 저장 중단. 기존 불완전 분석은 명확히 표시 |
| 음수 잔량·휴무일 실제 판매 | FRD의 확인을 거친 경우에만 저장. 값을 자동 0으로 바꾸지 않음 |
| 저장 용량 부족·권한 거부·DB 오류 | 트랜잭션 취소. 기존 자료·입력 유지, 재시도·백업 안내 |
| 다른 탭의 선행 변경 | revision 충돌로 중단·재조회 안내, 자동 덮어쓰기 없음 |
| 프로그램 시작 시 DB 읽기 실패 | 초기 샘플 재삽입하지 않음. 가능한 복원 경로 안내, 임시 저장 성공 표시 없음 |
| 백업 파일 생성 실패 | 실패 안내, 현재 DB 유지. 다운로드 성공을 허위 표시하지 않음 |
| 복원 구문·버전·연결 검사 실패 | 검사 위치·원인 안내. 기존 DB 변경 없음 |
| 화면 렌더링 오류 | 오류 경계 화면에서 재조회·재시작 안내. DB 자동 초기화 없음 |
| 배포 파일 전달 실패 | 네트워크·주소 확인 안내. 저장 자료가 지워졌다고 단정하지 않음 |

화면 오류는 쉬운 문장, 내부 오류는 `VALIDATION`, `DUPLICATE`, `CONFLICT`, `STORAGE`, `BACKUP_FORMAT`, `CALCULATION` 등 코드로 구분한다. 내부 진단에는 앱·자료 버전과 오류코드만 남기고 업무 데이터 전체를 기록하지 않는다.

DB 스키마·자료 스키마·백업 형식·계산 기준 버전을 분리한다. 새 앱이 기존 자료를 읽을 때 호환 버전을 확인하고, 필요한 변환은 검사 후 트랜잭션으로 수행한다. 변환 실패 시 기존 자료 유지·오류 안내. 지원하지 않는 미래 형식은 빈 자료로 처리하지 않는다. 기존 의미를 바꾸는 마이그레이션으로 FRD 계산 기준을 우회 변경하지 않는다.

배포 전 업데이트·롤백 호환 검사를 하고 데이터 변환이 필요한 배포는 사전 파일 백업을 권유한다. 1차에는 자동 클라우드 복구·원격 로그 수집·사용자 편집 이력 화면을 추가하지 않는다.

| 배포 | 운영 주소 새로고침·해시 이동·보안 헤더·파일 공개 범위·Preview 저장 분리 |
| 성능·개인정보 | 현재 자료 목표 시간 측정, 네트워크 요청에 실제 업무 자료가 없는지 확인 |

독립 기대값을 사용한다. 계산 함수로 예상값을 다시 만들어 같은 오류를 정상으로 판정하지 않는다. FRD 예시의 순매출 98,000원·메뉴 수익 73,500원·75.0%·매장 손익 41,500원을 기본 검사로 사용하고, 별도 소규모 재고 예제로 실사 전후의 기대 잔량을 손으로 정해 대조한다. 시안 예시 숫자는 정답으로 사용하지 않는다.

자동 검사에는 가상 자료만 사용한다. 브라우저 검사는 검사 전용 origin·프로필로 실행해 실제 운영자의 IndexedDB를 지우거나 복원하지 않는다. 네트워크 오류·저장 예외는 검사 환경에서 주입해 실제 장애 동작을 확인한다.

PRD 연결은 M1→판매, M2→비용, M3→수익성, M4→기간·손익, M5→재고, M6→저장·백업·복원이다. 1차 기능 누락·계산 불일치·저장 실패를 성공으로 표시하는 문제가 있으면 배포 완료로 판정하지 않는다.

## 16. 4시간 구현 계획과 남은 운영 정보

PRD의 기획 30분·화면 설계 20분·개발 115분·검사 45분·배포 30분, 총 240분을 유지한다. 이미 수행한 자료 검토·문서 작성도 기획 시간에 포함하므로 문서마다 새 4시간을 더하는 계획이 아니다. 실제 소요가 초과하면 검사·배포를 빼지 않고 상황과 범위 재협의 필요성을 보고한다. 4시간은 목표이며 완료 보장은 아니다.

개발은 공통 자료 형식·계산·저장 계층 → 판매·비용 → 수익성·손익·재고 → 백업·복원 연결 순으로 진행한다. 공통 입력·표·창을 재사용하고 서버·계정·다중 기기·2차 XLSX 라이브러리를 구성하지 않는다. 단순한 저장 자료 묶음으로 복원·실패 처리를 통일한다.

기술 구조는 이 문서로 정했다. 실제 GitHub 소유 계정·저장소 이름, Vercel 프로젝트·운영 주소, 상업/비상업 배포 용도에 맞는 요금제와 결제 승인은 배포 단계에서 실제 정보로 연결한다. 이 정보가 아직 없다는 이유로 기능·계산·사용 순서를 바꾸지 않는다. 본 작업은 TRD 저장까지이며 외부 저장소 생성·업로드·유료 결제·배포는 수행하지 않았다.
